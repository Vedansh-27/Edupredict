## Project Overview

EduPredict Cloud is a full-stack web application that uses a machine learning regression model to estimate a student's final examination grade (0–20 scale) from historical academic and personal features. It is deployed as a cloud-hosted REST API on Render (PaaS) and serves a responsive browser dashboard.

**This is an academic demonstration.** Predictions are statistical estimates and must not be used to make consequential decisions about individual students.

---

## Problem Statement

Educational institutions need early-warning mechanisms to identify students who may require additional academic support. EduPredict Cloud demonstrates how a cloud-deployed machine learning system can provide grade estimates from observable student features — enabling educators to have data-informed conversations rather than relying solely on intuition.

---

## Objectives

- Train and evaluate a regression model to predict student final grade (G3).
- Deploy the model as a cloud-hosted REST API (FastAPI on Render).
- Provide a polished, responsive browser interface.
- Demonstrate cloud architecture, PaaS deployment, security, input validation, and performance measurement.
- Produce all materials required for the FT-III Case Study evaluation.

## System Architecture

```
User / Browser (HTTPS)
        |
        v
Render Web Service (PaaS)
  FastAPI + Uvicorn
  |
  +-- GET  /           --> Jinja2 HTML dashboard (served inline)
  +-- GET  /health     --> Model status check
  +-- GET  /model-info --> Model metadata + evaluation metrics
  +-- POST /predict    --> Pydantic validation --> ModelService --> sklearn Pipeline --> JSON
  +-- GET  /docs       --> Swagger UI (auto-generated)
        |
        v
models/student_performance_model.joblib  (loaded once at startup)
models/model_metadata.json               (feature list, metrics)
```

**Deployment pipeline:**
```
Developer (git push) --> GitHub repo --> Render webhook --> Build (pip install + train) --> Start (uvicorn)
```

## Dataset Source and Limitations

### Source
**Synthetic dataset** generated by `ml/generate_synthetic_data.py` (649 rows, 16 columns, seed=42).

The synthetic data mirrors the statistical structure of the **UCI Student Performance Dataset**:
> P. Cortez and A. Silva. *Using Data Mining to Predict Secondary School Student Performance.*
> FUBUTEC 2008, Porto, Portugal, EUROSIS, ISBN 978-9077381-39-7.
> http://www3.dsi.uminho.pt/pcortez/student.pdf

### Why Synthetic
Automated downloading of the UCI dataset is fragile in CI/CD pipelines. A reproducible synthetic generator ensures deterministic builds without external network calls.

### Limitations
- Synthetic data does not represent real student populations.
- Statistical correlations are manually specified, not learned from real observations.
- A production system should use institutional data with proper ethics governance.

### Features Used

| Feature | Type | Range | Description |
|---------|------|-------|-------------|
| G1 | float | 0–20 | First period grade |
| G2 | float | 0–20 | Second period grade |
| studytime | int | 1–4 | Weekly study time |
| failures | int | 0–3 | Past class failures |
| absences | int | 0–74 | School absences |
| sex | str | M/F | Student sex |
| age | int | 15–22 | Student age |
| Medu | int | 0–4 | Mother's education level |
| Fedu | int | 0–4 | Father's education level |
| famrel | int | 1–5 | Family relationship quality |
| freetime | int | 1–5 | Free time after school |
| goout | int | 1–5 | Going out frequency |
| Dalc | int | 1–5 | Weekday alcohol consumption |
| Walc | int | 1–5 | Weekend alcohol consumption |
| health | int | 1–5 | Current health status |
| **G3** | int | 0–20 | **Target: final grade** |

## Model Training Methodology

1. **Data generation:** `ml/generate_synthetic_data.py` produces `data/student_performance.csv`.
2. **Preprocessing:** `sex` label-encoded (M=1, F=0); all numeric features scaled via `StandardScaler` inside a sklearn `Pipeline` (prevents data leakage).
3. **Train/test split:** 80/20, `random_state=42`.
4. **Candidates trained:** LinearRegression, Ridge, RandomForestRegressor, GradientBoostingRegressor.
5. **Evaluation:** MAE, RMSE, R² on held-out test set + 5-fold CV R² on training set.
6. **Selection:** Highest test R².
7. **Artifacts saved:** `models/student_performance_model.joblib`, `models/model_metadata.json`, `reports/evaluation_report.json`.

**No data leakage:** The scaler is fit only on training data. G3 (target) is never an input feature.

## Evaluation Metrics and Results

### All Models — Test Set Results

| Model | Test MAE | Test RMSE | Test R² | CV R² (mean ± std) |
|-------|----------|-----------|---------|---------------------|
| LinearRegression | 1.0059 | 1.2950 | 0.8711 | 0.8719 ± 0.0178 |
| **Ridge** ✅ | **1.0053** | **1.2942** | **0.8713** | **0.8719 ± 0.0177** |
| RandomForest | 1.0668 | 1.3794 | 0.8538 | 0.8582 ± 0.0190 |
| GradientBoosting | 1.1114 | 1.4123 | 0.8467 | 0.8403 ± 0.0166 |

**Selected model: Ridge Regression**
Ridge achieved the highest test R² (0.8713). Linear and Ridge are nearly identical — Ridge's L2 regularisation makes it slightly more robust. Tree-based models performed slightly worse, likely because G3 is highly linearly correlated with G1 and G2 in the synthetic dataset.

### Interpretation
- **MAE = 1.005** → average prediction error is ~1 grade point on the 0–20 scale.
- **RMSE = 1.294** → no catastrophically wrong predictions.
- **R² = 0.871** → the model explains 87.1% of variance in final grades.

### `POST /predict`

Accepts student features, returns predicted final grade.

**Request body:**
```json
{
  "G1": 12,
  "G2": 13,
  "studytime": 2,
  "failures": 0,
  "absences": 4,
  "sex": "M",
  "age": 17,
  "Medu": 2,
  "Fedu": 2,
  "famrel": 4,
  "freetime": 3,
  "goout": 3,
  "Dalc": 1,
  "Walc": 2,
  "health": 4
}
```

**Successful response (200):**
```json
{
  "predicted_score": 13.42,
  "score_scale": "0-20",
  "message": "Estimated final examination score (G3). This is a statistical estimate only.",
  "model_version": "1.0",
  "interpretation": "Good -- student is performing above average."
}
```

**Validation error (422):**
```json
{
  "detail": [
    {
      "loc": ["body", "G1"],
      "msg": "Input should be less than or equal to 20",
      "type": "less_than_equal"
    }
  ]
}
```

**Model unavailable (503):**
```json
{
  "detail": "Model is not currently available. Please try again later."
}
```

## Cloud Deployment — Render

### 1. Push to GitHub

```powershell
cd "C:\Users\Vedansh Garg\OneDrive\Desktop\EduPredict-Cloud"

```

### 2. Create Render Web Service

1. Go to https://dashboard.render.com → **New** → **Web Service**
2. Connect your GitHub repository.
3. Configure:

| Setting | Value |
|---------|-------|
| Runtime | Python 3 |
| Build Command | `pip install -r requirements.txt && python ml/generate_synthetic_data.py && python ml/train_model.py` |
| Start Command | `uvicorn app.main:app --host 0.0.0.0 --port $PORT` |
| Plan | Free |
| Health Check Path | `/health` |

4. Click **Create Web Service** and wait for the build (~3–6 minutes).

### 3. After deployment

- Your app URL: `https://edupredict-cloud-xxxx.onrender.com`
- Add this URL to `_ALLOWED_ORIGINS` in `app/main.py`.
- Commit and push — Render auto-deploys.

### Build & start commands explained

| Command | Purpose |
|---------|---------|
| `pip install -r requirements.txt` | Install all dependencies |
| `python ml/generate_synthetic_data.py` | Create `data/student_performance.csv` |
| `python ml/train_model.py` | Train model, save `.joblib` and metadata |
| `uvicorn app.main:app --host 0.0.0.0 --port $PORT` | Start ASGI server on Render-assigned port |

### Troubleshooting Render deployments

| Problem | Likely cause | Fix |
|---------|-------------|-----|
| Build fails: module not found | requirements.txt missing or incomplete | Verify file is committed |
| 502 Bad Gateway | Port binding error | Confirm `--port $PORT` in start command |
| Model not loaded (503) | Training step failed during build | Check build logs for Python errors |
| Cold start (30–60s first request) | Free plan spin-down | Normal; use paid plan to avoid |
| CORS error | Render URL not in allowed origins | Add URL to `_ALLOWED_ORIGINS` |

## Security Considerations

| Measure | Implementation |
|---------|---------------|
| Input validation | Pydantic on backend + JS on frontend |
| No hardcoded secrets | All configuration via environment variables |
| .gitignore | `.env` files excluded |
| HTTPS | Provided by Render (Let's Encrypt TLS) |
| Restricted CORS | Explicit allowed origins list |

| NaN/infinity guard | Checked on input and model output |
| No unnecessary PII | No personal student data stored |

## Scalability and Cost Analysis

### Current capacity (single Render free-plan instance)

| Factor | Details |
|--------|---------|
| Concurrency model | Async ASGI (Uvicorn) — handles I/O concurrency well |
| CPU bottleneck | sklearn Ridge inference is near-instant (~1–5 ms per call) |
| Memory | ~150–250 MB (Python + sklearn + pandas) |
| Cold start | 30–60s on free plan after 15 min idle |
| Horizontal scaling | Possible on paid plans (stateless API) |

### Scaling path

1. **Paid Render Starter (~$7/month):** Always-on, no cold starts.
2. **Horizontal scaling:** Multiple instances on Render Standard plan (API is stateless — no code changes needed).
3. **Database:** Add Render PostgreSQL ($7/month) if prediction logging is needed.
4. **CDN:** Cloudflare for static asset delivery.
5. **Dedicated ML inference:** AWS SageMaker or Google Vertex AI for high-volume production.

### Cost estimate (October 2024 — verify at render.com/pricing)

| Plan | Monthly cost | Features |
|------|-------------|---------|
| Free | $0 | 1 instance, cold starts, 512 MB RAM |
| Starter | ~$7 | Always-on, 512 MB RAM |
| Standard | ~$25 | Autoscaling available |

*Prices may change. Always verify current pricing at https://render.com/pricing.*

## Known Limitations

1. **Synthetic data** — not real student observations. Results are illustrative.
2. **Free plan cold starts** — first request after idle may be slow (~30–60s).
3. **No authentication** — prediction endpoint is publicly accessible.
4. **No model versioning** — only one model artifact is maintained.
5. **No monitoring** — no APM, alerting, or drift detection beyond Render's uptime ping.
6. **Linear model assumption** — Ridge is nearly linear; complex non-linear patterns would need more data and different models.
7. **SQLite not implemented** — prediction history is not stored. If needed, use Render PostgreSQL.
